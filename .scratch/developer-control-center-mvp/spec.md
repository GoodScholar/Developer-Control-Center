# Developer Control Center MVP

Status: ready-for-agent

## Problem Statement

个人全栈开发者经常需要为同一个开发项目同时启动前端、后端、数据库、缓存和其他长期运行的开发服务。现有工作流通常依赖多个终端窗口、零散脚本和人工观察：开发者必须记住启动顺序，判断服务是否真的可用，追踪分散日志，排查端口冲突，并在结束工作时确保所有子进程均已退出。

这种工作流缺少统一、持续且可信的项目运行视图。仅看到进程已创建，并不能说明服务已经健康；一个上游服务失败后，依赖它的下游服务仍可能被错误启动；应用或终端异常退出还可能留下难以识别的外部进程。开发者需要一款本地优先、跨平台且安全的桌面控制中心，在不接管开发环境、不引入云账户、也不扩大系统权限的前提下管理这些开发服务。

## Solution

Developer Control Center（工作名称）是一款 Apache-2.0 开源桌面应用，首版支持 macOS 13 及以上版本和 Windows 11。开发者可以注册本地开发项目，审核应用根据 `package.json` 和 Docker Compose 文件生成的检测建议，并将确认后的定义保存为仓库内、可版本控制的 `.devcontrol.toml` 项目配置。

应用按照服务依赖启动项目，持续展示项目与开发服务状态、预期端口、HTTP/TCP 健康检查和实时运行日志。开发者可以安全地执行 Start All、Stop All，以及单个开发服务的启动、停止和重启。应用只自动管理自己启动的受管进程；外部端口冲突始终要求开发者自行判断和处理。

应用使用 Web 技术构建桌面界面，Rust 本地核心负责系统能力。项目配置、本地元数据和运行日志均留在开发者设备上。首版无账户、无云后端、无默认遥测、无管理员权限要求。

## User Stories

1. 作为个人全栈开发者，我希望把一个本地目录注册为开发项目，以便从一个位置管理其中的开发服务。
2. 作为个人全栈开发者，我希望看到所有已注册开发项目，以便快速进入当前要开发的项目。
3. 作为个人全栈开发者，我希望多个开发项目可以同时运行，以便并行处理不同工作。
4. 作为个人全栈开发者，我希望取消项目注册时只删除应用本地记录，以免仓库内容或项目文件被修改。
5. 作为个人全栈开发者，我希望应用识别项目中的 `package.json`，以便快速获得 Node 开发服务建议。
6. 作为个人全栈开发者，我希望应用识别 Docker Compose 配置，以便快速获得容器组合命令建议。
7. 作为个人全栈开发者，我希望检测建议在执行前完整展示，以便确认应用理解了我的项目。
8. 作为个人全栈开发者，我希望能够修改检测建议，以便修正命令、参数、目录、依赖或端口。
9. 作为个人全栈开发者，我希望只有明确确认后才生成项目配置，以免自动扫描产生未经审核的可执行行为。
10. 作为个人全栈开发者，我希望确认后的项目配置写入仓库，以便通过版本控制审查和复现。
11. 作为个人全栈开发者，我希望同一份项目配置可以在 macOS 和 Windows 使用，以便跨设备保持一致工作流。
12. 作为个人全栈开发者，我希望只为确有差异的命令声明平台覆盖，以免维护两份完整配置。
13. 作为个人全栈开发者，我希望配置中的路径相对于开发项目根目录，以便仓库在不同设备上保持可移植。
14. 作为个人全栈开发者，我希望配置包含明确模式版本，以便未来升级时得到可解释的迁移结果。
15. 作为个人全栈开发者，我希望应用在外部编辑器修改项目配置后重新读取并校验，以便将配置作为正常仓库文件维护。

## Implementation Decisions

- 项目采用工作名称 Developer Control Center；品牌命名不阻塞 MVP，配置协议名保持 `.devcontrol.toml`。
- 源码采用 Apache-2.0 许可证，以允许宽松复用并提供明确专利授权。
- 首版支持 macOS 13 及以上版本和 Windows 11；两端的项目配置、启动、停止、日志、端口和健康检查语义必须一致。
- 桌面架构采用 Tauri 2，界面采用 React、TypeScript 和 Vite，Rust 核心负责所有本地系统能力。
- 建立一个深的 Control Center 模块作为 UI 与测试共享的主要接口。调用者提交项目注册、配置、运行和历史操作意图，模块返回状态快照、事件和可操作错误。
- Tauri 通信层保持轻薄，只负责把桌面界面的用户意图转换为 Control Center 模块调用，并把事件推送回界面。
- Host Runtime 是 Control Center 模块内部的真实适配缝。macOS、Windows 和自动化测试分别提供适配器；适配器负责进程树、信号、端口、时钟和受限文件访问等平台行为。
- 项目配置模块负责解析、校验、迁移和保存 `.devcontrol.toml`，并保证无效配置不会进入执行阶段。
- `.devcontrol.toml` 位于开发项目根目录，包含 `schema_version = 1`，所有路径相对于开发项目根目录。
- 项目配置具有跨平台共享默认值，并允许 `macos` 和 `windows` 局部覆盖程序、参数或环境值；不维护两份完整配置。
- 项目配置可以包含非敏感环境值和外部 `.env` 文件引用。环境变量值不得进入界面事件、运行摘要、普通错误或诊断包。
- 开发服务默认以结构化程序和参数启动；Shell 执行必须在项目配置中显式开启。
- 自动检测模块首版只分析 `package.json` 和 Docker Compose 文件。检测输出是无执行权限的检测建议，用户确认后才由项目配置模块写入仓库。
- 开发工具预检只报告缺失程序和修复方向，不下载、安装或切换运行时。
- 运行协调模块以服务依赖图调度启动。依赖图必须无环；存在循环时项目配置校验失败并给出可操作错误。
- 没有依赖关系的开发服务可以并行启动。某个分支失败时，独立分支继续；依赖失败分支的下游进入阻塞状态。
- Start All 是幂等操作：已处于 Starting、Running 或 Healthy 的服务不重复启动；停止、失败或阻塞的服务按当前依赖条件处理。
- 单服务启动、停止和重启通过同一个运行协调模块执行。上游重启不自动级联，但界面必须展示可能受影响的下游。
- 服务状态包括 Stopped、Starting、Running、Healthy、Unhealthy、Stopping、Failed 和 Blocked。未配置健康检查的稳定存活进程以 Running 作为可用状态；配置健康检查的服务只有 Healthy 才达到可用状态。
- 项目状态包括 Stopped、Starting、Running、Degraded、Stopping 和 Needs Attention。所有目标服务可用时为 Running；至少一个目标服务失败、不健康或阻塞时为 Degraded。
- 健康检查只支持 HTTP 和 TCP。启动阶段默认每秒检查一次并在 60 秒超时；运行阶段每 5 秒检查，连续失败三次转为 Unhealthy，连续成功两次恢复 Healthy。默认值允许按服务覆盖。
- 开发服务异常退出后转为 Failed 并触发通知；首版不自动重启。
- 预期端口为可选配置。应用在启动前检查已声明端口，并可将 HTTP 服务入口交给系统浏览器打开。
- 外部端口冲突显示端口、PID、进程名和可复制的处理命令。应用不提供自动终止外部进程按钮，也不请求提权。
- Stop All 按依赖图反向停止。每个受管进程默认获得 10 秒优雅停止时间，超时后终止其完整进程树；超时允许按服务覆盖。
- 应用异常退出后，不根据旧 PID 自动接管或终止仍在运行的进程。重启后将其识别为外部进程并进入 Needs Attention 流程。
- 运行日志采集标准输出与标准错误，保留 ANSI 表现信息，但首版日志面板只读，不提供终端输入或 PTY 交互。
- 合并日志按采集时间组织所有服务输出，每条记录保留来源服务。界面支持 All Services、单服务筛选、搜索和复制。
- 日志默认保留七天，并设置 500 MB 全局上限；任一限制先达到时清理最旧日志。
- SQLite 保存项目注册、本地界面偏好和运行摘要；持续日志使用独立限额文件，不以大字段写入 SQLite。
- 应用采用单实例模型，一个实例管理所有项目和项目运行，避免多个实例同时操作本地元数据与受管进程。
- 关闭主窗口时应用驻留系统托盘。显式退出应用时提示停止全部运行中项目；应用退出后不支持继续管理独立服务。
- 配置文件发生外部变化时自动重新读取和校验；应用提示用户应用变更，但不静默重启运行中的服务。
- 保存影响运行中服务的配置后，界面提示重启相应服务；是否重启由用户决定。
- 系统通知仅用于服务失败、健康恶化和需要处理的端口冲突，正常状态变化不通知。
- 核心界面为项目列表和项目详情两级。项目详情同时呈现服务列表、项目与服务状态、端口、健康信息和日志。
- 配置通过结构化表单编辑，并提供在外部编辑器中打开原始配置的入口；首版不实现内置代码编辑器。
- 界面首版使用英文，跟随系统明暗主题，并为核心导航和操作提供键盘访问与清晰焦点状态。
- 应用默认无账户、无云后端、无遥测。网络只用于用户配置的健康检查和 GitHub Release 版本检查。
- 文件访问限制在用户注册的开发项目、用户明确选择的环境文件和应用自身数据目录。
- 诊断包只能由用户主动导出，并在生成时移除环境变量值和可识别密钥内容。
- 清除历史数据删除运行摘要、日志和界面状态，但保留项目注册和仓库内项目配置。
- MVP 不随系统登录启动，也不自动启动任何开发项目。
- 首个 Alpha 通过 GitHub Releases 提供 macOS 和 Windows 安装包、校验和及源码。Alpha 可以暂未签名，但必须清楚说明；稳定版前完成签名与公证。
- 首版只检查并提示新的 GitHub Release，不自动下载或安装更新。
- 目标规模为最多注册 50 个项目、同时运行 5 个项目、每个项目 10 个开发服务。
- 性能目标为无项目运行时平均 CPU 低于 1%、空闲内存目标低于 200 MB、管理 10 个持续输出日志的服务时界面无明显卡顿、日志可见延迟目标低于 500 毫秒。

## Testing Decisions

- 测试只验证通过模块接口可观察到的行为，不依赖内部函数、私有状态、线程数量、数据库表布局或具体平台命令拼接。
- 主要测试缝是 Control Center 模块接口。绝大多数行为测试通过提交用户意图并断言状态快照、事件、持久结果和可操作错误完成。
- Host Runtime 提供自动化测试适配器，用可控进程、端口、时钟、健康响应和文件系统场景验证运行协调，而不在每个测试中创建真实操作系统进程。
- 项目配置模块通过公开解析和校验行为测试模式版本、相对路径、平台覆盖、依赖循环、环境引用、未知字段和无效值。
- 自动检测模块通过临时示例项目测试 Node 和 Docker Compose 检测建议，重点验证“建议不可执行”和“确认后才写入”的外部行为。
- 运行协调模块通过 Control Center 接口测试依赖图、并行分支、阻塞传播、幂等 Start All、反向 Stop All、单服务控制和非级联重启。
- 状态测试覆盖全部服务状态和项目聚合状态，尤其区分 Failed、Blocked、Unhealthy、Degraded 与 Needs Attention。
- 健康检查测试使用可控时钟和响应序列验证 60 秒启动超时、运行检查间隔、三次失败阈值及两次成功恢复阈值。
- 进程生命周期契约测试验证优雅停止、10 秒超时、完整进程树终止，以及应用异常退出后不自动接管旧 PID。
- 安全测试验证外部进程不会被自动终止、项目外路径被拒绝、Shell 模式需要显式配置、密钥值不会进入事件、日志、错误或诊断包。
- 日志测试验证 stdout/stderr 采集、ANSI 信息保留、来源服务标记、合并顺序、搜索筛选、七天保留和 500 MB 全局清理。
- 持久化测试通过公开模块行为验证项目注册、运行摘要、配置热重载和清除历史数据，不断言 SQLite 内部表结构。
- UI 测试重点验证项目列表、项目详情、配置审核表单、服务操作、状态呈现、合并日志、错误说明、键盘导航和焦点状态。
- 第二个测试缝是少量真实桌面验收测试：添加示例项目、审核检测建议、生成配置、Start All、查看状态和日志、Stop All，并确认无遗留受管进程。
- 真实桌面验收测试分别在 macOS 和 Windows CI 上执行，以覆盖 Tauri 通信、Web UI、安装构建和真实进程生命周期。
- 跨平台 Host Runtime 适配器共享同一组契约测试，保证两端对启动、停止、状态、端口和错误的核心语义一致。
- 性能测试验证既定空闲资源预算、10 服务日志场景和 500 毫秒日志可见延迟目标。
- 仓库目前没有实现代码或既有测试，因此不存在可沿用的测试先例；首个实现票据应先建立上述两个测试缝，再通过纵向行为逐步扩展。

## Out of Scope

- AI Coding Agent、Agent Session 或 Git Worktree 管理。
- 一次性任务、数据库迁移、代码生成、Runbook 或通用命令中心。
- 内置交互终端、PTY 输入或完整终端模拟器。
- Docker 容器、镜像、卷、网络或虚拟机的直接管理。
- Node、Python、Rust、Java、Docker 或其他开发环境的自动安装和版本切换。
- 除 `package.json` 和 Docker Compose 之外的自动项目检测器。
- 云同步、用户账户、远程机器、团队协作、审批或权限系统。
- 自动重启、无限重试或后台自愈开发服务。
- 自动终止外部进程或任何管理员/root 提权流程。
- 应用内自动下载和安装更新。
- Mac App Store、Microsoft Store 或其他应用商店发布。
- 系统清理、开发缓存分析、磁盘分析或 Mole 功能复刻。
- 自定义主题系统和首版多语言界面。
- 应用随系统登录启动或自动启动最近开发项目。
- 产品正式品牌命名；MVP 期间继续使用工作名称。

## Further Notes

- MVP 完成标准是在 macOS 和 Windows 上均可安装并运行，能够检测包含 `package.json` 和 Docker Compose 的示例项目，经用户确认生成有效项目配置，按依赖启动三个服务，展示状态、日志、端口与健康信息，并在 Stop All 后不遗留受管子进程。
- 单服务失败必须正确阻塞其下游，独立分支继续工作，项目进入 Degraded；端口冲突、配置错误和异常恢复必须给出可操作说明。
- 配置热重载、日志保留、诊断脱敏、最小目录权限和异常退出恢复均属于 MVP 验收范围，不是发布后的补充优化。
- 自动化测试必须在 macOS 与 Windows CI 上通过，安装包构建和真实桌面关键路径属于发布门槛。
- 详细领域术语以项目领域词汇表为准；长期架构约束以现有 ADR 为准。
- 本规格状态为 `ready-for-agent`，下一阶段应拆分为带显式阻塞关系的纵向示踪票据。
